# Prompt to Discovery / Builder performance — technical design

- Date: 2026-09-29
- Status: Written specification for review; no implementation approval
- Trace baseline: `cb66557978ae3f7393257affaaf254c1ff379519`
- Accepted New Trip dependency inspected read-only: `0860d4ff87ca26323d9f04d29f941b7b93b123a3`

## Purpose and evidence

An independent traveller should be able to continue shaping a multi-stop trip promptly after submitting either selected stops or a free-text brief, while Morrovia still distinguishes confirmed places from interpretation, unresolved intent and a route that has passed planning checks. The change shortens the path to **useful, editable planning**, not merely the time to a new loading screen. It preserves the traveller's work, occurrence identity and Morrovia's route-quality rules.

The source trace confirms that `HomeTripStarter` awaits `/api/journey-capture` before navigating for Describe. That endpoint can await sequential model attempts, provider place resolution and optional planning-suggestion validation. The Builder starts handoff lookups independently, but `resolveHandoffBatch` returns one `Promise.all` result that the Builder publishes only after every lookup settles. In a synthetic fixture, a sibling finished at 102 ms but publication waited 3,502 ms for a slow lookup. Deterministic and fake-provider fixture timings from the investigation are diagnostic only. There is **no measured live or optimized-app end-to-end baseline, and no achieved speedup** yet. The hypothesis that route assessment materially blocks first useful paint remains unproved; profile it before changing that calculation.

The accepted New Trip work is not in the trace baseline. It adds the shared controlled planner, direct submission into the mounted Builder, `resolveNewTripEntryState`, and `homepageSemanticInputFingerprint` in `lib/easyt/home-trip-handoff.ts`. This spec depends on those accepted semantics. Implementation must integrate that accepted history with the local candidate through the normal reviewed integration process before editing overlapping owners; this specification does not merge, rebase or copy that branch. Coordinate one executor for `home-trip-handoff.ts`, `home-trip-starter.tsx`, `trip-builder.tsx`, `new-trip-starter.tsx` and their tests. Do not carry forward the baseline's provider-derived draft fingerprint as an intake-edit test.

## Critical paths and ownership

| Stage | Current path | Proposed path |
| --- | --- | --- |
| Homepage Stops | Validate selected places → project `HomeTripDraft` → durable handoff → navigate → Builder hydration → batch lookup publication | Same durable handoff and navigation; known canonical occurrences become editable at hydration; independent lookup results publish as they become usable. |
| Homepage Describe | Validate → await complete `/api/journey-capture` including provider enrichment → project → durable handoff → navigate → Builder hydration | Validate → durably preserve frozen traveller input and reservation → navigate → Builder displays pending intake → Builder requests **essential interpretation** → projects into its canonical state → resolves missing place facts per occurrence. |
| Direct New Trip Describe | Controlled planner awaits capture and passes the complete result to mounted Builder | Controlled planner passes the validated frozen input into the **already-mounted Builder**; Builder alone requests interpretation, without navigation or a second handoff round trip. |

`HomeTripStarter` owns only homepage controls, submission latch, owner/revision guard, existing `commitHomepageHandoff` storage boundary and navigation. `NewTripStarter` owns controlled fields but hands submission to `TripBuilderDocument`. `TripBuilderDocument` remains the sole interpretation-request coordinator, canonical trip/route mutation owner, recovery and persistence owner for both entries. `lib/easyt/home-trip-handoff.ts` remains the shared intake/receipt/projection validator. `/api/journey-capture` and `lib/easyt/journey-capture.ts` remain the interpretation owners; place intelligence retains provider resolution. Existing Discovery, clarification, route assessment, schedule, nightly allocation and save owners are unchanged. No client capture starts on the homepage after a Describe handoff, and no client capture starts in both `NewTripStarter` and Builder.

### Exact minimum navigation gate

Before homepage navigation, validate active input and prepare the **existing owner-scoped intake snapshot and existing handoff slot** through the staged-write/rollback preservation boundary. The frozen submission contains the original prompt or selected-stop entries, active mode, selected canonical occurrence IDs and order, dates and explicit date clear, origin/end selections and explicit clears, traveller count, budget, interests/preferences with selected/untouched/cleared states, owner ID, input revision, semantic input fingerprint, opaque handoff token, and its reserved trip ID. Inactive mode buffers may remain in the ordinary editable intake snapshot, but they are not submitted or interpreted. The frozen copy must remain available if the editable snapshot changes after submission. Private input stays in browser storage, not the URL; the URL retains only the existing handoff discriminator.

The gate waits for **successful read-back/validation of those local writes and existing current-trip preservation**, not model extraction, geocoding, imagery, route commentary or provider inventory. If any write or preservation step fails, keep the current page/input and current trip pointer, show the existing actionable save/recovery error, and do not navigate. A storage rollback failure must leave the old intake recoverable rather than treating a partial record as valid. A previous unconsumed handoff cannot be overwritten until its work is protected by the established recovery path. Owner mismatch, mismatched URL token, stale input revision or invalid receipt fails closed.

### Cross-tab handoff ownership

All transitions that read or change an owner's existing intake receipt or the matching Homepage handoff envelope must use **one owner-scoped cross-tab critical section** in the existing `lib/easyt/home-trip-handoff.ts` owner. This includes Homepage Stops and Describe submission, direct New Trip submission, ordinary Homepage/New Trip edits, import departure snapshot preservation, pending Edit/discard, and completion or cleanup after Builder recovery. The existing `commitHomepageHandoff` boundary participates in that same serialization; it cannot replace a different unacknowledged pending token. The transition re-reads current storage **inside** the critical section and validates owner, handoff token, reserved trip ID, input revision and semantic fingerprint before changing either existing key. A retry of the exact token may converge on the same reservation; a different pending token cannot be overwritten. Rollback of a partial two-key write occurs within that critical section and must not restore an older value over another tab's newer work. If the browser cannot provide the required cross-tab serialization, fail the affected transition closed and retain recoverable input rather than claiming a durable reservation. This does not introduce a new storage namespace or persistence owner.

### Pending receipt and canonical acknowledgement

Use a versioned **pending interpretation** variant of the existing handoff envelope/receipt, in the same storage owners. This is a state of the existing handoff, not a new draft, job store or trip model. The pending receipt has owner, handoff token, reserved trip ID, submitted input revision and `homepageSemanticInputFingerprint(frozenSnapshot)`. Its reader recomputes that semantic fingerprint from the **frozen** snapshot and requires an exact owner/token/revision match; a later edit to the ordinary editable snapshot does not rewrite submitted meaning. It has **no projected-draft `inputFingerprint` and is never accepted by `homepageHandoffReceiptForOwner` as a completed `HomeTripDraft`**. The accepted `semanticInputFingerprint` helper remains the sole source for traveller-controlled meaning. `inputFingerprint` retains its current role: verify a projected draft after interpretation. Legacy version-1 projected handoffs continue through their current exact receipt/draft path.

Builder validates the pending envelope and reserves its trip ID before any save effect. It hydrates the frozen input as **received / pending interpretation**, not as a validated route. Builder requests essential capture once per active submission generation. On a valid result, it projects via the existing `projectHomepageInput`/Builder application seam, computes the projected draft fingerprint, and applies that projection to the same Builder trip ID only if owner, token, revision and generation still match. The in-memory projected draft and its fingerprint must pass the existing projection checks; raw input never masquerades as that draft. Keep the frozen pending envelope until the existing canonical recovery acknowledgement has durably saved and verified the corresponding trip, including its input/occurrence binding. Then the existing exact-match cleanup may retire the envelope. If capture succeeds but save has not acknowledged, reload repeats interpretation under the **same** token and trip ID. If canonical recovery already contains that ID, resume it first and never create another. If a crash occurs between recovery save and cleanup, the existing trip wins over the pending envelope.

`saveTripRecovery(...).stored === true` remains the canonical durable document acknowledgement. Replacing the pending receipt with a completed projected receipt, and retiring or replacing its Homepage envelope, is a separate **serialized receipt transition** after that acknowledgement; Builder must not perform those writes outside the owner-scoped critical section. It must re-read and match the exact still-current pending token before committing completion. If another tab edited or replaced intake first, an old completion cannot overwrite its receipt or envelope. If receipt completion is delayed or fails, the canonical saved trip remains resumable by its reserved ID and the pending source remains recoverable; do not claim the whole handoff finished or allow a new-trip exit that depends on completion. A retry may complete only the same token. If the traveller explicitly edits after canonical acknowledgement, the edited intake detaches from that completed trip and its next submission receives a fresh identity under the accepted New Trip receipt contract.

For direct New Trip, the same owner-scoped intake/semantic receipt mechanism records a pending submission and the mounted Builder's reserved trip ID. It does **not** call `commitHomepageHandoff`, write a navigation handoff, or route `/journey/new` back to itself. If reload occurs before a canonical document can safely represent pending interpretation, the existing intake record remains the durable source and the entry-state gate resumes that same reservation; it must not show a fresh starter or allocate a second trip. The accepted entry precedence remains explicit `?trip=`/`?recover=` → current Builder draft recovery → exact URL handoff/template → pending direct intake → genuinely fresh entry. When canonical recovery acknowledges the trip, it takes precedence over pending intake for that ID. A trip saved elsewhere in My Trips does not replace deliberately fresh intake.

Retries with semantically unchanged frozen input reuse the same pending token and reserved trip ID. A quick double activation starts one request. Cancellation aborts where possible and invalidates the generation even if a provider ignores abort; the durable input remains until the traveller deliberately discards it or a replacement is safe. Editing/removing/reordering while pending invalidates old work. A subsequent submission of that edited **unacknowledged** intake rotates token/revision but stays within the same reserved Builder trip; no old response may apply. Once a canonical trip is completed, accepted New Trip rules govern: unchanged semantic fingerprint cannot reseed it; materially edited intake is detached and receives a new submission identity on next submit. A legacy completed receipt lacking semantic fingerprint cannot be auto-reseeded or guessed edited. Exact legacy URL handoff and reserved-trip recovery remain available. Template and import handoffs keep their current precedence and do not enter pending Describe capture.

## Essential interpretation and optional enrichment

The current `/api/journey-capture` combines essential interpretation with optional provider work. Its active semantic path may run the planning model, a second attempt/fallback, `captureJourneyBriefFromSemanticIntent(..., openWorldProvider)`, and `canonicalizePlanningSuggestions` before returning. The latter helper already accepts an omitted provider and can project validated semantic intent through deterministic place models; `captureJourneyBrief` also supplies the deterministic fallback. The smallest server change is a narrowly requested **intent-only response mode on the existing capture endpoint/client**, using the existing model routing and validation but omitting provider place lookups and planning-suggestion canonicalization from that response. Preserve existing full-response behavior for other callers until they intentionally adopt the staged contract. Avoid a second interpretation engine or a new endpoint family.

The intent response must retain all named/source-spanned geography, roles, order, hard constraints, endpoint and date semantics, structured brief and truthful ambiguity/coverage status. Validation of model output, source coverage and fallback remains mandatory. Provider incompleteness alone must no longer reject otherwise valid essential semantic interpretation or force another model attempt. If semantic model output is invalid or misses named intent, use the existing deterministic/fallback path and expose unresolved mentions; never erase them or promote a guess to canonical. A broad country/region remains an area needing existing Discovery, not a fabricated overnight city. High-value model destination suggestions and assessments are advisory: they may arrive later through an existing bounded request/validation path, only as reviewable suggestions. They never silently add stops or gate the first useful workspace. No SSE, WebSocket, worker queue or generic streaming subsystem is introduced.

The response can still take as long as *essential* model interpretation requires. Homepage navigation becomes earlier because it no longer waits for it. For Describe, actual useful planning begins when trustworthy canonical places or an actionable clarification are available; this design does not promise a one-second interpretation of arbitrary prose. Optional imagery, descriptions, commercial inventory and provider metadata cannot return the entire workspace to loading or change the traveller's selection.

## Occurrence-level resolution contract

Extend the existing `resolveHandoffBatch` / Builder resolution seam with an incremental per-occurrence outcome callback (or a narrow equivalent in the same owner) while preserving a final summary for existing consumers. Do not publish only after `Promise.all`. The input is an ordered list keyed by stable occurrence ID; repeated names remain distinct. A canonical selection with sufficient existing identity is usable immediately and is not reinterpreted merely to add imagery/coordinates. A missing coordinate may still be verified later without replacing its selected canonical identity. Every named but unresolved mention retains an ordered placeholder and a confirmation/retry path; no timeout drops it to make a route appear complete.

States are `pending`, `resolved`, `needs-confirmation` and `failed`, with explicit `timeout` as a recoverable failure reason. The first eligible result is published when it completes, independent of slow siblings. Limit external lookups to three concurrent occurrences initially; retain the existing bounded per-request geocode deadline (currently 4 seconds, capped at 10) and provider-owned bounds, then calibrate from measured live behavior rather than shortening them to hit a screenshot target. Abort on scope change and use a per-session promise cache for identical permitted lookups, keyed by provider/query/context; **do not deduplicate occurrence state or selected identity**. Retry only failed/timeout scopes, leaving successful results and traveller edits intact. Provider failures keep truthful partial/empty/error distinctions.

Before applying **every** async interpretation or resolution outcome, check the active owner, handoff/submission token, frozen semantic fingerprint and input revision, current request generation, and occurrence ID. Confirm that the occurrence still exists and its current user-selected identity has not changed. A late response for an edited, removed, reordered or superseded occurrence is discarded. Reordering does not rename occurrences; application uses current order rather than a captured array index. An account switch cancels/invalidates all requests and prevents old private input from rendering. Optional results never steal focus, shift active controls or reset a route the traveller has edited.

## First-useful workspace and correctness

For **Stops**, Builder presents the selected canonical occurrences, their order and editable route controls after hydration, before optional lookup work. If some entries are unresolved, show them in place with their status and existing clarification action. For **Describe**, Builder first shows the preserved input with edit/cancel/retry controls and honest pending status. This is orientation, **not** the first-useful planning milestone by itself. Once essential interpretation supplies a trustworthy selected/confirmed place, show it in the editable structure; where it supplies a broad area or ambiguity, open the existing actionable Discovery/clarification flow. Do not show speculative extracted text as a confirmed stop.

Keep the present route validator, fixed commitments, nights, leg feasibility, clarification and recovery rules authoritative. A partially editable structure is not a verified ready route. Route-ready requires the current canonical document to pass the same existing readiness checks, including all required occurrences and blocking issues; optional enrichment completion is separate. Do not defer a measured decision-critical check merely to improve first paint. Reuse current compact status/feedback components and Storybook patterns; no fabricated progress percentage, countdown or large loading-copy treatment. In implementation, inspect `docs/design-system.md`, shared controls/stories and the closest Builder/Discovery production surfaces before editing UI. Preserve readable mobile controls and no focus movement from background updates.

## Recovery and failure acceptance

| Case | Required result |
| --- | --- |
| Exact canonical Stops; repeated Tokyo → Kyoto → Tokyo | Show selected ordered occurrences promptly. IDs and each visit's separate route/day binding survive interpretation, reload and edits. |
| Ordinary Describe; broad country/region; mixed known/unresolved | Preserve prompt and choices. Interpret with current semantic/fallback rules; show known places independently and send broad/ambiguous intent to existing Discovery. No unresolved destination disappears. |
| Fast sibling plus slow/hanging lookup | Publish the fast occurrence before the slow deadline; slow one remains pending, then recoverable timeout/failure. Successful sibling is not restarted on retry. |
| Provider failure, invalid semantic result or offline | Keep intake and any valid canonical results. Distinguish failure from genuine empty, offer scoped retry/edit, and do not claim route ready. |
| Edit, remove or reorder during work; rapid resubmit or cancel | Preserve current user choice/order. Old generation cannot apply, remount, navigate or create another trip. |
| Reload before interpretation or after partial resolution | Resume the same reserved trip/intake. Unacknowledged source remains durable; acknowledged canonical recovery wins. Reissue only required work. |
| Completed receipt: same versus edited; legacy receipt | Same cannot reseed; edited detaches from completed receipt; legacy completed never auto-reseeds. Exact valid unconsumed/URL and reserved-trip paths still work. |
| Owner/account switch; mismatched token/fingerprint | Fail closed. No other owner's prompt or draft is shown or saved. |
| Import/template and existing Builder recovery | Preserve their precedence and existing canonical paths; no duplicate capture or new trip. |
| Failure while preserving handoff or acknowledging canonical recovery | Do not navigate on failed initial preservation. Retain pending input until verified canonical recovery; retry keeps identity and explicit clears. |
| Two tabs submit, edit, import or finish the same owner's intake at once | Serialize all receipt/envelope transitions; re-read and match the exact token under the lock. The losing stale transition cannot erase or resurrect another tab's work. Missing cross-tab serialization fails closed. |

Tests must exercise these as behavior, including storage-fault injection and a provider that ignores abort, not only source-structure assertions. Existing homepage, New Trip, import/template, Builder/repository/recovery, Discovery, repeated-stop and route-readiness tests remain intact. No UI-audit allowance or existing test should be weakened.

## Measurement and release evidence

For each attempt, mark: (1) submit activation, (2) durable intake verified, (3) Builder shell visible, (4) first actionable planning content, (5) required interpretation/resolution complete, (6) route ready, and (7) optional enrichment complete. An error or abandoned attempt has its own terminal outcome, not a fabricated completion. Stops **actionable** means a known selected occurrence and its usable edit/route controls are rendered. Describe **actionable** means at least one trustworthy interpreted canonical occurrence with usable controls or an open, selectable existing clarification/Discovery decision. A shell, spinner, repeated prompt or disabled control does not count. Route-ready is measured only after existing blocking validation passes.

Carry one opaque attempt identity across homepage navigation using the handoff token and local performance marks; direct New Trip uses the Builder submission identity. The identity is for local correlation and deduplication, not a prompt-bearing URL or new analytics platform. Record stage durations and categorical outcomes in local diagnostics. Any product analytics uses existing `trackEvent` consent checks, bounded/coarsened durations and allow-listed categories from `docs/product/jtbd-analytics.md`; never emit raw prompts, names, coordinates, trip documents, notes, provider response bodies or private receipt contents. Avoid logging a recoverable input in server timing diagnostics.

Implementation acceptance must record matched before/after runs for exact Stops, ordinary Describe, broad area, mixed known/unresolved, repeated occurrences, and slow/failing provider, plus reload and cancellation. Separate fixture timing from live providers, and cold from warm cache/model runs. Use the optimized **local application** for release-representative browser measurements, rather than development compilation latency; inspect at 390, 430, 768, 1024 and 1440 CSS pixels where UI changes. Report medians and tails, sample count, environment, first-actionable definition and failures. Rough aspirations remain ~1 second for acknowledgement/navigation and ~1–2 seconds for useful known structured content; report actual outcomes and do not assert those targets for every free-text prompt.

## Boundaries and review questions

This ticket adds no new persistence owner, queue, route engine, global loading framework, model/parser replacement, speculative destinations, account cross-over or generic streaming protocol. It does not change booking, provider attribution or optional analytics consent. The accepted New Trip history must be integrated first or in the same reviewed implementation branch; the trace candidate alone is not a correct implementation base.

Implementation planning should confirm the exact shape of the versioned pending envelope and the existing recovery write that first acknowledges it. That choice must satisfy the receipt and crash-order rules above without another storage namespace. It should also verify whether essential semantic-model response time, rather than provider enrichment, dominates real Describe first-actionable latency; the design makes no unmeasured speed claim. These are implementation interface checks, not permission to weaken the ownership or durability contract.
