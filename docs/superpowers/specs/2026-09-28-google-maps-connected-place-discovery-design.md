# #346 Actual Google Maps and connected place discovery

**Status:** technical design for review; no product implementation authorised by this document alone.

**Base:** `f6dd263550d3eccdd9bbf388423d0fa2e6882668`

**Existing spike HEAD:** `9a97a31fe039fedfe223b639b1c6e4283b4a6eea` on `codex/google-places-enrichment-346`.

## Traveller job and scope

In the expanded authenticated Trip Map, a traveller explores an actual Google map, selects a native Google POI or a Morrovia place, inspects available facts, then deliberately saves it or adds it to the right day. Reopening the trip must retain the choice. The existing route and day context remain visible. This replaces the spike's Google-labelled list beside MapLibre; it is one connected workspace, not a second map mode.

The feature remains flag-off by default. Builder, Overview, inline Itinerary and Transport maps, public Route Detail and homepage/demo maps stay on their existing lightweight MapLibre/static owners. Separate Explore keeps its accepted category system. No route engine, Google Directions/Routes, geolocation prompt, generic map-provider framework, new trip/itinerary owner, or other product surface is introduced. The custom Places presentation described below is conditional on the billing-jurisdiction gate; it is not automatically approved for an EEA billing account.

## Current owners and reason for the screenshot defects

`JourneyMapPlannerWorkspace` already owns the canonical trip, selected stop occurrence/day, route legs, Plan/Stay/Eat/See tabs, saved ideas, and the mobile map sheet. `JourneyPlannerMap` owns its MapLibre canvas. The #346 spike mounts `MapPlaceEnrichment` inside the existing `finderDock` behind an “Explore with Google Maps” toggle. That child owns another See/Eat/Stay/Practical category strip and list/detail state, while the parent can also show a selected-place context panel. On mobile the parent sheet, Shape the day dock, and child detail contribute repeated handles, headings and close controls. The fix must remove the duplicate ownership in the integrated state, not cover it with CSS.

Existing `PlaceEnrichmentProvider`, `google-place-enrichment.server.ts`, `EnrichedPlace` normalisation, authenticated API route, flag, request cancellation and tests are useful starting points. `saveItineraryIdea` / `scheduleItineraryIdea`, accommodation selection and the shell's canonical mutation/save path remain authoritative. `MapResultPlace` already coordinates other map result selection; Google selection must join the parent selection model with its distinct provider identity, rather than run in a nested child model.

The existing Storybook Delhi/Agra/Jaipur story repeats fixed Delhi place records in all three stops. This is fixture contamination, not proven production behaviour; acceptance fixtures must become scope-correct.

## Workspace architecture and map lifecycle

`JourneyMapPlannerWorkspace` chooses one canvas for the expanded authenticated Map after its existing availability check: a narrowly scoped Google Maps JavaScript adapter when flag and complete configuration are valid, otherwise the existing map/failure presentation. The adapter receives canonical overlay data and selection/camera commands; it emits typed map interactions. It does not own trip mutation, route calculation, selected day or persisted state. Google SDK loading is lazy, single-flight, and absent from flag-off or unrelated pages. Switching category or loading details does not remount the map or reset the camera. No automatic nearby request is tied to `idle`/pan/zoom; a traveller may explicitly choose Search this area if that interaction is justified by the final UI.

The browser key is restricted by HTTP referrer and Maps JavaScript API. A separate server key remains restricted to the Places API and never enters client code. Proposed local names are `NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY`, `NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID`, existing `GOOGLE_PLACES_API_KEY`, and existing `MORROVIA_GOOGLE_PLACE_ENRICHMENT=enabled`; exact required Map ID and API enablement must be checked against the chosen current Maps JS marker/canvas API before code. Availability must report missing browser configuration as unavailable rather than rendering a Google label over MapLibre. Only ignored local environment files hold values. Do not print keys or alter cloud configuration from this branch.

The Google canvas starts at the selected canonical stop coordinates. Whole route fits trustworthy mapped stops once on explicit request; stop selection focuses that occurrence. Camera padding uses measured desktop panel or mobile sheet occlusion so the selected place remains visible. Ordinary pan/zoom stays native. If route geometry is included, verify its provenance and permission for use on Google first; otherwise show a clearly schematic connection between canonical stops without implying road directions. Never call Google Routes/Directions just to redraw a leg. Canonical stop, item and leg IDs stay distinct from Google Place IDs. Markers for stops, planned activities and saved permitted place references map back to those IDs. Custom hit areas must not consume every basemap click or overlap each other where a list alternative is needed.

## Selection and discovery contract

The parent owns one discriminated selection: whole route, stop occurrence, leg, activity/pin, Google place (`placeId`), or empty map. A selected Google place also carries the stop occurrence and intended day context at the time of selection; moving the camera never silently changes that context. Choosing another stop or category invalidates incompatible detail/list responses by request generation or abort, while preserving canonical saved state. Do not match repeated destinations by display name or array index.

Use Google's documented map click event: only an `IconMouseEvent` with a `placeId` is a native clickable POI. Stop the default POI info window when Morrovia handles that event, and request details by Place ID through the existing authenticated server endpoint. A click on a Morrovia custom marker selects its own canonical/result identity; an empty map click follows the existing dismissal or explicit Add pin behaviour. Do not scrape map labels, reverse-geocode every click, disable POI interaction, or claim all buildings are clickable. List selection and custom Google result marker selection call the same parent select-place action. One details request path serves all three entry points, including a selected saved reference; the browser map never independently fetches the same Places details.

Keep Plan/Stay/Eat/See as the only top-level workspace tabs. Remove the spike's provider-mode toggle, child category strip and repeated Back to day planning button. Practical places may be reached through an appropriate filter or grouped result within See rather than a second top-level strip. Desktop shows one results-or-detail panel beside the map; selecting a place replaces list content with detail. Mobile uses the existing single map sheet and one header/handle/collapse or close system. The `MapPlaceEnrichment` logic can be split into data/result/detail composition under the parent, but must not retain independent category, selection or mobile sheet state. Back to places restores the destination occurrence, category, fetched results and list scroll position; no automatic refetch may erase that context while it is still valid. Keyboard users can select every fetched place and trip item from an ordered list without relying on map markers.

## Place facts, photos and reviews

The selected-place detail uses the existing normalized place as its base: name, category, address, rating/count, current open state and hours, website and Google Maps link when supplied. Group decision-critical facts and planning action before secondary disclosures. “Open now” is about the current provider response, not the traveller's future day. Missing facts remain absent. Basic detail loads first; selected-place photo and available written reviews may arrive progressively and fail independently. No list-wide photo/review fetch, city-photo substitution, review scraping, fabricated booking confidence, price, duration, distance, or full-review-inventory claim.

Extend server normalisation with only the fields required for selected-place media/reviews. Use supported photo media access and permitted response fields. Render external text as text and allow only validated outbound URLs; do not proxy arbitrary URLs. Show required Google attribution plus each applicable photo and review author/source credit and link from returned metadata. The Google map's own attribution remains unobscured. These details are ephemeral provider content and must not enter `EasyTTrip`.

## Planning, persistence and the terms boundary

Selection is inspection. Save for later or Add to day is a separate explicit action. Add first confirms the canonical stop occurrence and day; use `itineraryIdeaDayOptions`/existing chooser if selected day does not belong to that stop or the destination is ambiguous. A pan far away must not label a POI “near” the original stop. Double activation must be idempotent. Preserve existing multi-day scheduling, remove/Undo and canonical save/reload behaviour. A hotel goes through the existing accommodation-choice path, not an activity row, and is never labelled booked merely because selected or saved.

The old idea model stores `title`, optional coordinates, area, image and source URL, and `scheduleItineraryIdea` copies title/coordinates into map/day rows. Calling `itineraryIdeaForLocalPlace` on a Google response would persist Google facts and leak them to downstream MapLibre previews. **That conversion is forbidden for this feature.** The proposed narrow persisted identity is a provider reference (Google Place ID), the canonical `stopId`/optional `dayId` and daypart, a stable traveller-choice ID, and explicit user-authored text only when actually entered by the traveller. This may require a tagged source/reference extension to `ItineraryIdea` and a reference-aware schedule renderer, with legacy ideas unchanged. Do not store raw provider name, coordinates, address, rating, hours, reviews, photos or photo URLs as if authored. Reopen resolves provider facts by Place ID on demand. If resolution fails, preserve a truthful saved-place reference and its day/stop binding with retry or reselection; do not invent a stale name or silently discard the choice.

**Durable Place ID lifecycle:** Store provider-reference resolution freshness (for example, the last successful ID-only refresh time) with the reference, without persisting Google place facts as Morrovia-owned content. Google currently permits Place ID storage indefinitely and recommends refreshing IDs older than 12 months. When an ID reaches that age, use the supported Place Details ID-only refresh path where applicable, then resolve current display facts on demand. `INVALID_REQUEST` means the reference is invalid; `NOT_FOUND` means it is obsolete. Either leaves the saved/scheduled reference and canonical stop/day binding intact, with a retry or traveller-led reselection state. Never silently rematch an obsolete ID by a stored Google name, mutate its identity to a search result, or turn returned provider text into user-authored content. Legacy non-Google itinerary ideas and their rendering remain unchanged.

Before implementation, trace each saved item through Overview, Itinerary, Explore, Map previews and repository serialization. Do not render custom Google Places API content in association with MapLibre; any EEA Places UI Kit presentation needs its own explicit terms review. Show a neutral saved-reference treatment or an outbound Google link where needed. Distinguish Saved, Added to day and Booked. Reuse the current shell mutation and persistence owner; no new client storage or database of Google details.

### Billing-jurisdiction architecture gate

Before the implementation plan commits to a Places presentation path, inspect the **actual Google Cloud billing-account address** for the project and record whether the applicable agreement is EEA or non-EEA, including any negotiated terms that supersede the public terms. Founder nationality, current location and traveller location do not establish billing jurisdiction. If the billing address or applicable agreement cannot be verified, leave the Places presentation decision open and keep #346 blocked at this gate.

- **Non-EEA billing account:** The proposed actual Google Maps canvas with custom server Nearby/Details flow may proceed only under the applicable [non-EEA Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms), [Places API policies](https://developers.google.com/maps/documentation/places/web-service/policies), attribution rules and caching/storage restrictions. Never display that Places content in association with MapLibre or any other non-Google map.
- **EEA billing account:** Do not assume that the same custom Places list/detail architecture is permitted. The current [EEA Service Specific Terms](https://cloud.google.com/terms/maps-platform/eea/maps-service-terms) restrict Places API content other than latitude, longitude and `place_id` from use **“With any Map”**, including a Google map, and limit other Places API content to the published [EEA Places API Permitted Uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses). Explicitly evaluate Places UI Kit because the current EEA Places restrictions exempt it; verify its own attribution and caching terms and whether it can support the approved travel-planning loop. If a compliant presentation cannot be established, keep #346 blocked rather than silently implementing the non-EEA architecture.

This gate also covers photo/review display, Place ID refresh and all downstream saved-reference surfaces. The public terms are a review baseline, not a substitute for the actual agreement. No code path, fixture or flag may declare the connected Places experience accepted until the applicable branch is recorded and its presentation/persistence checks pass.

## Failures, request bounds and privacy

Scope each nearby response to stop occurrence, category and search area; abort or discard obsolete responses. Preserve valid current-scope results during partial failure. Use compact existing status components: confirmed empty “No places found”; lookup failure “Couldn't load places” with Try again; stay failure “Couldn't load stays” with Try again. A failed load never reports zero ideas. A failed photo/review request leaves basic detail usable. SDK, quota, key or offline failure preserves trip, navigation and planning controls with a truthful local recovery state. If MapLibre is used as fallback, remove Google-derived overlays and content that cannot be shown on it; do not recreate the spike's mixed Google-list/MapLibre layout.

Nearby searches are bounded and deliberate. Details are on selection, photo/review fields only for that selection, with cancellation and safe short-lived in-memory deduplication where terms permit. Do not continuously search during panning. Do not send full trip documents, personal notes or unrelated user data to Google. The server route remains authenticated, `no-store`, with bounded Place IDs, coordinates and category inputs. No new provider or analytics identity is needed; use privacy-safe existing event conventions.

Measure one Maps JS load, Nearby, Details, photo media and retry calls separately. Record actual field masks and then-current SKU categories from Google's [field selection guidance](https://developers.google.com/maps/documentation/places/web-service/choose-fields) and [pricing](https://developers.google.com/maps/billing-and-pricing/pricing). Budget alerts are not a cap; a live test requires restricted keys, bounded quotas and a small agreed usage budget. No cloud changes are authorised here. Actual billing jurisdiction cannot be inferred from the user's current location.

## Acceptance and review sequence

1. **Real map milestone:** In the actual local authenticated expanded Map, load Google canvas, zoom and click a native POI absent from the fetched list, receive its Place ID via map click, inspect server-fetched detail, then select canonical stop and leg. Repeat on mobile. Fixture clicks alone do not pass.
2. **Coherent discovery:** One top-level category strip, one desktop detail owner, one mobile sheet/header, no nested handles or duplicate Shape the day headers. Native POI, list and custom result marker all resolve to one detail. Back to places restores the correct stop/category/results position. Rapid switching cannot display stale scope data.
3. **Planning loop:** Pick a stop occurrence and correct canonical day, Add/Save deliberately, prevent double writes, remove/Undo where supported, hard reload and reopen. Hotel selection follows accommodation choice. Verify legacy ideas and repeated same-name stops. Test ID-only freshness, an ID older than 12 months, `INVALID_REQUEST`, `NOT_FOUND`, retry/reselection, and preservation of the saved reference without persisted Google facts.
4. **Interaction principles:** Mobile custom controls are at least 44 × 44 CSS pixels with spacing; Add, Back, close, category and map controls remain reachable; custom markers do not block native POIs; selected place stays visible around sheet occlusion; keyboard list covers places/trip items; no focus theft or accidental Add. Google attribution remains visible.
5. **Resilience and scope:** Distinct Delhi/Agra/Jaipur fixtures; no-photo/review/hours, empty, partial failure, total failure, invalid/absent key, quota, offline and SDK rejection. Verify Google content cannot leak into disallowed MapLibre previews. Keep legitimate current-scope results on partial failure.
6. **Responsive and tests:** Inspect 390, 430, 768, 1024 and 1440 px plus narrow/mobile keyboard and long labels. Run focused provider/map/selection/itinerary/persistence suites, typecheck, `audit:ui`, `build:check`, Storybook build and `git diff --check`. Use production components in Storybook stories and read actual story IDs from the index. Browser acceptance is mandatory because a Storybook fixture cannot prove native POI clicks.

After this design is approved and the billing-jurisdiction gate is resolved, write a test-first implementation plan with focused phases: Google canvas/native POI and canonical overlays; a jurisdiction-permitted list/detail/mobile presentation and progressive content; permitted planning persistence/downstream references and Place ID lifecycle; failure/cost safeguards and real responsive/live acceptance. Review that plan before product code. The source remains local on `codex/google-places-enrichment-346`; do not push, deploy, trigger CI, modify main/staging, or use production/staging databases. Missing local live credentials yield **LIVE MAP GATE UNVERIFIED**, never a fixture-based pass.
